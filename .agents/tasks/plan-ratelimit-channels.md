## What exists today (from reading the code)

- `bot.py` has two scheduled loops:
  - `daily_post` (at `POST_TIME` in `TIMEZONE`) calls `post_daily(channel)` for every id in `daily_channel_ids()`; `post_daily` sends QOTD, then `send_crossword`, then `send_wordsearch`. So there are three features in this loop.
  - `hangman_daily` (00:00:30 UTC) sends the AREDL hangman board (with yesterday's reveal note) to every id in `daily_channel_ids()`.
- `daily_channel_ids()` = every `storage.data["settings"][gid]["channel_id"]` plus `DEFAULT_CHANNEL_ID` (env `DAILY_CHANNEL_ID`). `answer_channel_ids(day)` = today's `puzzle_channels` + the same settings channels + `DEFAULT_CHANNEL_ID`.
- `/setchannel` (guild_only, `default_permissions(manage_guild=True)`) writes `settings[gid] = {"channel_id": channel_id}` and replies publicly. `/postnow` (same perms) posts QOTD + crossword + word search to the current channel.
- Message path: `DailyBot.on_message` → `handle_hangman(message)` (single letter in a board channel, or a reply to a board; replies publicly with an embed and saves state) → otherwise `handle_answer(message)` (crossword/word search answers like `1. apple`; reacts ✅/❌, saves state, may send "completed" message). Both call `storage.save()` (full JSON rewrite) per guess, which plus the API calls is the real cost to protect.
- Slash commands: qotd, crossword, wordsearch, progress, yesterday, leaderboard, setchannel, postnow, hangman start|guess|giveup. The tree is `app_commands.CommandTree(self)` created in `DailyBot.__init__`.
- discord.py 2.7.1 `CommandTree._call`: if `interaction_check` returns False it sets `command_failed` and returns silently (no `on_error`, no log). Autocomplete interactions also pass through `_call`.

## Decisions

1. Daily features inventory: four features, ids `qotd`, `crossword`, `wordsearch`, `aredl` (the hangman). Commands: `/set-daily-qotd`, `/set-daily-crossword`, `/set-daily-wordsearch`, `/set-daily-aredl`. `/postnow` is a manual command, not a daily feature, and keeps posting QOTD + crossword + word search to the current channel unchanged.
2. One channel per feature per guild (same cardinality as the old `/setchannel`). Setting again replaces it.
3. Command shape:
   - `/set-daily-<feature> [channel]`: optional `channel: discord.TextChannel | None = None`; omitted = the channel the command is run in (text channel or thread). Sets that feature for this guild.
   - `/unset-daily feature:<choice>`: one command with choices `qotd`, `crossword`, `wordsearch`, `aredl`, `all`. Turns the feature OFF for this guild (stored tombstone, also suppresses the `DAILY_CHANNEL_ID` fallback for this guild). Rationale: a single command with a dropdown keeps the command list short (8 unset commands would be clutter) and "off" must be an explicit state anyway because of the env fallback.
   - `/daily-channels`: ephemeral list of every feature for this guild with its post time and where it will post (channel mention(s), `off`, or `not set`), marking the env default as `(DAILY_CHANNEL_ID)`. It uses the exact same lookup the loops use, so it shows what will really happen.
   - `/setchannel` STAYS as a "set all four features to this channel" shortcut (the README setup step and existing admins rely on it). Its description becomes "Send all daily posts (question, puzzles, hangman) to this channel".
4. Permissions: all five setup commands (`set-daily-*`, `unset-daily`, `daily-channels`, `setchannel`) use `@app_commands.guild_only()` and `@app_commands.default_permissions(manage_guild=True)`, same as today's `/setchannel`. All replies are ephemeral (this changes `/setchannel` from public to ephemeral).
5. Channel validation in set commands: target must be a `discord.TextChannel` or `discord.Thread` (else ephemeral error). Compute `perms = target.permissions_for(interaction.guild.me)`; require `view_channel`, `embed_links`, and `send_messages` (for threads `send_messages_in_threads`). If any is missing, reply ephemerally naming the missing permissions and store nothing. For `crossword`/`wordsearch` additionally warn (don't block) if `add_reactions` or `read_message_history` is missing, since answer reactions need them.
6. Storage schema (in `storage.py`):
   - `DAILY_FEATURES = ("qotd", "crossword", "wordsearch", "aredl")` module constant.
   - `data["daily_channels"]`: `{guild_id_str: {feature: channel_id_int | None}}`. A missing feature key = not configured; `None` = explicitly off.
   - `data["daily_legacy"]`: `{guild_id_str: [feature, ...]}` features whose value came from migration and haven't been touched by a new command since.
7. Migration (runs in `Storage.__init__`, one-time, idempotent): for each `settings[gid]` with a `channel_id`, pop `channel_id`, set every feature not already present in `daily_channels[gid]` to that channel, record those features in `daily_legacy[gid]`, delete `settings[gid]` if it's now empty, then `save()` once if anything changed. The `settings` top-level key itself stays (defaulted as today). Because `channel_id` is popped, migration cannot re-run and undo a later `/unset-daily`. Rollback note (README not needed): old code would need `/setchannel` again.
8. `DAILY_CHANNEL_ID` fallback rule (`Storage.daily_targets(feature, default_channel_id, default_guild_id)`): targets = every non-None `daily_channels[*][feature]`, plus `default_channel_id` unless its guild (`default_guild_id`) has an explicit entry for that feature that is NOT in `daily_legacy` for that guild. If `default_guild_id` is unknown (`None`, channel not in cache), include it (old behavior; the loop then logs if it can't reach it). Result: a guild that used both `/setchannel X` and `DAILY_CHANNEL_ID=Y` keeps getting everything in both X and Y after deploy (exactly as before) until an admin runs a new set/unset command for a feature, which is an explicit action. No silent stop for any pre-existing configuration.
9. `Storage.set_daily_channel(guild_id, feature, channel_id | None)` stores the value and removes `feature` from `daily_legacy[gid]` (deleting the gid key when empty). Unknown feature → `ValueError`. `/setchannel` calls it for all four features.
10. Rate limiter: token bucket in new module `ratelimit.py`. `RateLimiter(rate: int, per: float, *, clock=time.monotonic, sweep_every=60.0)`: capacity `rate` tokens, refilling `rate/per` tokens/second; `hit(key) -> Verdict(allowed: bool, retry_after: float, notify: bool)`. `notify` is True only on the first blocked hit since the key's last allowed hit (that's the "once per cooldown window" notice). `clock` is a public attribute so tests can inject a fake clock.
11. Eviction: a bucket idle for `>= per` seconds has refilled to full, so dropping it is lossless. `hit` calls `sweep(now)` at most once every `sweep_every` seconds, removing all such buckets; `sweep()` is public and returns the number removed; `__len__` returns the bucket count (for tests). Memory is bounded by keys active in the last ~`per + sweep_every` seconds.
12. Limits and defaults (constants in `ratelimit.py`, overridable via env in `bot.py`, format `"<count>/<seconds>"`, e.g. `5/10`):
    - `RATELIMIT_COMMANDS` default `5/10`: per user, all slash commands.
    - `RATELIMIT_GUESSES` default `6/10`: per user, message-driven game guesses (hangman chat guesses + crossword/word search answers).
    - `RATELIMIT_CHANNEL` default `5/5`: per channel cap on message-path guesses the bot acts on (each acted-on guess produces a public reply/reaction). 5 per 5 s matches Discord's own per-channel message limit, so a group can't make the bot queue 429s or flood a channel.
    - `ratelimit.parse_rate(text, default)` returns `default` for `None`/empty, and logs a warning and returns `default` for invalid input (non-integer count, count < 1, seconds <= 0, wrong format). No "off" switch (YAGNI).
13. Where the limiter hooks in:
    - Slash commands: a single central hook. `class RateLimitedTree(app_commands.CommandTree)` overrides `interaction_check`: only for `interaction.type is discord.InteractionType.application_command` (autocomplete and others pass), key = `interaction.user.id`. Blocked → if `verdict.notify`, `await interaction.response.send_message(f"⏳ Slow down, try again in {n}s.", ephemeral=True)` where `n = max(1, math.ceil(retry_after))` (wrapped in `try/except discord.HTTPException`), return False. Later blocked hits in the same window get no response (Discord shows its own "did not respond" to that user only). `DailyBot.__init__` uses `RateLimitedTree(self)`.
    - Message path: NOT at the top of `on_message`, because counting ordinary chat would silently eat a chatty user's guesses. Instead one helper `allow_guess(message) -> bool` (user bucket first, then channel bucket; silent) is called at the point each handler has decided the message is a real guess and before any state change, save, reaction, or reply: in `handle_hangman` right after the prefilter (before `hangman.Game(...)`/`g.guess`), returning True when blocked so it doesn't fall through to `handle_answer`; in `handle_answer` right after `if result is None: return` (before the ❌ reaction). The CPU-only prefilters (channel check, `answers.parse`, `game.check`) run before the limiter; that is fine, they do no I/O.
14. Admin exemption: none. Admins/Manage Server are limited like everyone (setup commands are low-volume; guess limits apply to all).
15. Hangman reveal wording: behavior unchanged (only the 00:00 UTC post to AREDL daily channels reveals yesterday's level). README wording is corrected to say the reveal is in the AREDL daily channel (`/set-daily-aredl`).
